## Actualizador y concurrencia

El bloqueo `ormuz-content-update` se mantiene para nativo, externo, diario y
recibos públicos ya existentes. Checkout de main se realiza dentro del bloqueo.
`monitor-update-receipt.json` se crea **solo tras validaciones del actualizador**,
se persiste con su commit y se excluye de Pages. El diario no puede prepararlo
para commit. Su `validated_at` acredita validación del pipeline, no nuevos hechos
marítimos ni terminación de Pages.

El recibo se valida contra workflow exacto, evaluación y verified_at, estructura,
fecha no futura y números positivos de ejecución. Un recibo inválido se ignora.
Una ejecución nativa de run_number posterior se conserva; un trigger antiguo solo
se coalesce si ya lo superó un monitor validado del mismo V7 hace <50 min. Una
re-ejecución con run_attempt superior es elegible. El límite temporal evita
bloqueo indefinido si se recrea el workflow y reinicia su contador. El manual
explícito sin inputs conserva su capacidad de recuperación.

Dos triggers nuevos pueden producir dos comprobaciones serializadas: es un coste
aceptado para no omitir una actualización legítima. La prevención fuerte cubre
writers concurrentes, UUID externos duplicados, ejecuciones antiguas ya cubiertas
y pushes no fast-forward. No se afirma exactamente una comprobación por franja.
GitHub conserva una sola ejecución pendiente por grupo y puede sustituirla;
`cancel-in-progress:false` no ofrece una cola durable de todas las solicitudes.

Pages serializa build/deploy/verificación/avisos bajo su grupo separado. No se
añade dependencia updater→Pages mientras mantenga el bloqueo de contenido, por
lo que no se introduce un ciclo de espera. Un push concurrente a main puede hacer
fallar un push del bot; no se fuerza ni sobrescribe. Las notificaciones marítimas
siguen desactivadas y mantienen su prueba HTTP previa; no se conectan al receptor
técnico nuevo.

Tras el push del monitor, el resumen del job y el artefacto de Actions
`monitor-run-<run_id>-<attempt>` conservan UUID, evaluación y `written_commit`.
No son archivos de Pages ni un almacén confidencial: los lectores del repositorio
pueden acceder a sus artefactos. Solo contienen metadatos técnicos sin secretos.
Si falla su exportación/subida, se señala un warning y Pages puede publicar el
commit ya persistido; el recibo del monitor queda también en ese commit. Una
subida auxiliar no debe impedir publicar datos válidos. La cadena se comprueba
por recibo/resumen/commit, no por la hora de V7.

## Estados ambiguos y salud

| Caso | Conducta preparada |
|---|---|
| Dispatch POST sin respuesta | Intento guardado antes del POST; error inmediato, no reenvío ciego |
| 204 aceptado, run todavía ausente | Pendiente hasta 30 min; después error; sigue sin reenvío |
| Run en cola/en ejecución | Espera; >45 min desde el intento produce `recovery_run_overdue`; no duplica |
| Run correcto sin nuevo V7 | `recovery_completed_without_new_v7_verification`; no se declara recuperado |
| Fallo/cancelación/timeout terminal comprobado | Error visible; reintento solo después de ≥90 min y máximo tres por verificación |
| Límite agotado | `recovery_retry_limit_exhausted`; exige intervención, conserva estado |
| Verificación nueva por otra vía | Se registra publicación observada sin atribuirla al App; la causalidad requiere recibo/run/commit |
| Token de alcance/fecha/repositorio incorrectos | No dispatch; revocación de cualquier token recibido |
| Revocación fallida | Error explícito aunque el dispatch ya se aceptó; revisar credenciales y runs, no repetir a ciegas |
| Worker reiniciado o pausado | Estado persistente; lease 10 min; un owner vencido no puede escribir/enviar |
| Último tick interrumpido | `/health` detecta intento incompleto >5 min y fallos internos, además de informe >45 min |
| V7 supera 3 h durante una lectura lenta | Se vuelve a evaluar el reloj en el manifiesto final, no solo al empezar |
| Receptor caído/acuse incorrecto | Incidencia de entrega persistente y 503, incluso si se recupera V7 |

El umbral de 45 min de un run es diagnóstico; no cancela jobs ni prueba un fallo
definitivo de GitHub. El acuse del receptor acredita aceptación, no lectura del
destinatario. El monitor no puede avisar por sí mismo si todo Cloudflare o su
receptor están caídos: la comprobación adicional del endpoint privado sigue
pendiente de autorización. Tampoco puede ejecutar el motor fuera de los runners
si toda la API/infraestructura de GitHub falla.

## Validación y decisión

Pruebas preparadas: suite Python completa, mantenimiento, JavaScript de interfaz
y vigilancia, construcción, enlaces, privacidad, regresión de seis artículos y
46 recursos aprobados, sitemap y TAR exacto de Pages. Evidencias de CI se enlazan
en la PR para su SHA exacto. No se publica ninguna exportación privada ni se
registra una revisión humana inexistente.

El runtime local de Cloudflare con SQLite real y transporte de red simulado
comprobó: lectura fresca 200, reinicio con contador persistido creciente y V7 de
181 min con diario reciente 503 (`v7_stale`). No hubo requests App/receptor.
El primer ensayo Windows falló con rutas SQLite largas; al usar una ruta privada
corta el mismo fixture y código pasaron. Es una limitación del entorno local,
no evidencia de funcionamiento ni de consumo en Cloudflare Free real.

La propuesta técnica elimina los riesgos concretos identificados; la suficiencia
del plan Free, la cadencia externa, la cuenta App, el receptor y la recuperación
real **siguen sin verificarse**. Esta auditoría prepara la autorización de código
y de B por separado; no autoriza fusión, C o D. No se ha ejecutado ningún workflow
histórico de instalación ni se ha cambiado DNS, hosting o visibilidad.
